> 핵심은 코드를 작성할 땐 코드를 읽는 사람이 이해하는데 들이는 시간을 최소화할 수 있게 작성해야한다.


## 기본 규칙
#### 이름을 작성할 땐 읽는 사람이 오해하지 않게 만들어라

뜻이 명확한 단어를 사용하라.

#### 더 넓은 범위에서 사용되는 코드일수록 자세하게 이름을 지어라

작은 범위에서 사용되는 코드는 맥락으로 이해되는 경우가 많다.

## 주석
명명된 파라미터(Named parameter) 주석 트릭

Python은 Named parameter를 지원하는 언어 중 하나다.

```python
def connect(host, port):
    ...
...
connect(host = "127.0.0.1", port = 4242);
```

C, C++ 같이 Named parameter를 지원하지 않는 언어라도 주석으로 Named parameter를 흉내낼 수 있다.
```cpp
connect(/* host = */ "127.0.0.1", /* port = */ 4242);
```

#### 결함 주석
변화하고 성장하는 시스템에서 결함이 없을 수 없다.
결함을 문서화하는걸 두려워하지 마라.
아래 표를 보고 상황에 맞게 결함이 있는 부분에 주석을 달자.

| 표시   | 의미                            |
|--------|---------------------------------|
| TODO:  | 아직 하지 않은 일               |
| FIXME: | 오동작을 일으킨다고 알려진 코드 |
| HACK:  | 아름답지 않은 해결책            |
| XXX:   | 위험! 여기 큰 문제가 있다       |

```cpp
// XXX: 덧셈을 안하고 뺄셈을 함!
int sum(int lhs, int rhs) {
    return lhs - rhs;
}
```

## 조건문
#### 비교 구문을 작성할 땐 유동적인 값을 앞에 두고 고정적인 값을 뒤로 두는 편이 좋다.
```cpp
if (IQ > 100) {
    ...
}
```

IQ가 100보다 큰지 물어보는게 100이 IQ보다 작거나 같은지 물어보는 것보다 낫다.

```cpp
if (100 < IQ) {
    ...
}
```

## 단순화

#### 부정문보다 긍정문을 사용하는게 좋다.
```cpp
if (!useLogging) {
    ...
}
```
대신 아래 코드를 쓰자.
```cpp
if (useLogging) {
    ...
}
```

#### C언어에서 goto 활용
아래 코드에서는 goto가 꽤 유용해보인다.
```c
if (ptr == NULL) goto cleanup;

...

cleanup:
    free(p_ptr);
    free(c_ptr);
    ...

return;
```

#### 중첩된 코드를 피하라
중첩된 코드는 읽는 사람을 피곤하게 만든다.
- Early return으로 중첩된 코드 지우기

```cpp
if (isA) {
    ...
    if (isB) {
        ...
    }
    else return;
}
else return;
```
아래 코드처럼 바꾸자
```cpp
if (!isA) return;
...
if (!isB) return;
...
```

#### short circuit eval 남용하지 않기

short circuiot evaluation을 활용하면 깔끔한 표현을 할 수 있다.

```cpp
// A가 참이면 B를 평가하지 않는다.
if (A || B) {
    do_something();
}
```

아래 코드는 깔끔한 표현과는 거리가 멀어보인다.

```cpp
if (!(pptr = getParentNode(ptr)) || isLeftNode(ptr, pptr)) return;
...
```

아래 코드처럼 바꾸자.

```cpp
Node* pptr = getParentNode(ptr);
if (isLeftNode(ptr, pptr)) return;
...
```

#### C++ 매크로 트릭

```cpp
#define ADDFIELD(filed)  add_to->set_##field(add_from.field()) + add_to->field())
```

#### 상관없는 하위 문제 추출하기
코드의 목적을 파악 -> 직접적으로 목적을 위해 필요한 코드인가? 필요하지만 하위문제를 해결하는 코드인가? -> 알맞게 분리한다.
일반적인 목적의 코드를 프로젝트의 특정 코드에서 분리하라

#### Defragmenting

커다란 함수 안에 있는 코드를 재조직하여 그 안에 여러 개의 독자적인 논리영역이 있는 것처럼 만들 수 있다.

### 쉬운 말로 설명하기

쉬운 말로 자신의 생각을 지식이 부족한 사람에게 전달하는 기술은 매우 소중하다.

### 필요하지 않은 기능을 제거하고, 과도한 작업(overengineering)을 피하기

### 코드베이스를 최대한 작고 가볍게 유지하기

- 라이브러리에 친숙해지기
- 유닉스 도구 활용하기

### 다른 프로그래머가 수정하거나 새로운 테스트를 더하는 걸 쉽게 느낄 수 있게 테스트 코드는 읽기 쉬워야 한다.

### 일반적인 설계원리를 따르면 덜 중요한 세부 사항은 사용자가 볼 필요 없게 숨겨서 더 중요한 내용이 눈에 잘 띄게 해야한다.

### `Test_<함수이름>_<상황>` 과 같은 형태를 이용한다.
"함수명을 너무 길지 않게 한다"는 일반적인 원리가 적용되지 않는다. 테스트 함수명은 실질적으로 하나의 설명문처럼 기능한다.

> 어떤 코드는 다른 코드보다 테스트하기 더 쉽다. 테스트하기 좋은 코드는 잘 정의된 인터페이스를 가지고, 지나치게 많은 상태나 '설정'을 요구하지 않으며, 감추어진 데이터를 포함하지 않는다.

> TDD... 이는 매우 뜨거운 논쟁을 야기하는 주제인데, 여기서는 이 문제를 다루지 않을 것이다. 우리가 이야기하고 싶은 것은, 코드를 작성하면서 테스트를 염두에 두면 확실히 더 나은 코드를 만들 수 있다는 사실이다.

- 실제 코드 테스트를 가능하게 하는 것은 반드시 윈-윈 상황이 되어야 한다. 

> 무엇보다도, 테스트의 수정이나 추가가 쉬워야한다.
